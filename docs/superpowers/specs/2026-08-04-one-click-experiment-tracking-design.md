# Hermes 一键全流程与按日期收益追踪设计

## 1. 目标

在现有「选股流程」页提供一个「一键全流程」按钮。用户点击一次后，后端完成真实数据更新、规则扫描、舆情采集、DeepSeek 多 Agent 研判，并把规则、AI、混合、基准四组当日结果统一落库。

当前批次在四组结果落库后结束。未来交易日到达后，每次再次运行一键流程时，系统利用刚更新的行情自动补齐历史批次的买入价和到期收益。工作台按信号日期集中展示各组结果、成交状态与收益。

“自动运行”只指点击按钮后的业务流程自动执行，不包含 Windows 开机自启、计划任务或系统服务。

## 2. 范围

### 2.1 本次实现

- 配置 OpenAI 兼容接口 `https://api.pie-xian.com/v1`，默认模型 `deepseekv4flash`。
- 密钥只从 Windows 用户环境变量 `WORKBENCH_AI_API_KEY` 读取，不写入仓库、YAML、数据库或日志。
- 扩展现有 `POST /api/pipelines` 和 `PipelineManager`，不新建重复的前端串联流程。
- 在 `p3_foundry.html` 增加唯一主按钮、步骤进度、失败原因和四组结果摘要。
- 建立可复现的实验批次与决策台账。
- 以信号日的下一交易日开盘价作为买入价，追踪 `T+1/T+3/T+5/T+10` 收益。
- 在现有台账页面按信号日期、实验组、成交状态追踪，不新增独立页面。

### 2.2 不在本次范围

- Windows 开机自启或定时自动触发。
- 实盘下单、券商接口和自动卖出。
- 在一键流程中自动运行滚动回测或机器学习训练；本轮先按日期积累可复现的真实实验台账，作为后续评估输入。
- 在样本不足时宣称策略有效。
- 为得到正结果而反复修改实验口径。

## 3. 一键流程

一次批次共用同一个 `run_id`、`as_of` 和 `data_cutoff_at`：

1. **配置预检**：检查 Tushare 数据能力、DeepSeek 配置、密钥环境变量和数据库可写性。配置不完整直接失败，不启动半条流程。
2. **交易日历更新**：先联网更新交易日历，再确认最新完整交易日，避免“日历过期导致闸门拒绝、闸门拒绝又无法更新日历”的循环阻塞。
3. **市场数据更新**：更新行情、基础指标、资金流和权威涨跌停价格；每项记录来源、数据日期、行数和覆盖率。
4. **历史收益回填**：只处理已经到达买入日或目标日的旧批次。当前批次尚无未来数据，保持待回填。
5. **完整性闸门**：校验最新交易日、股票覆盖率、关键字段缺失率和数据截止时间。不达标则整批失败，不沿用旧数据伪装成功。
6. **规则扫描与舆情采集**：复用现有策略、扫描、新闻去重和来源追溯能力。
7. **DeepSeek 多 Agent 研判**：使用相同 `as_of` 和候选池，运行粗筛、三分析师、辩论与风控；模型漏字段、非 JSON 或请求失败均显式失败。
8. **四组结果落库**：在同一冻结候选池和同一数据截止时间下保存规则、AI、混合、基准四组结果，随后把本批次标记为成功。

前端只负责提交任务和轮询状态。浏览器刷新或离开页面不会中止后端任务，再次打开页面可恢复当前进度。

## 4. 四组实验口径

四组必须共享 `run_id`、`as_of`、候选池哈希和数据截止时间。本轮记录统一的开盘买入价格收益，不混入尚未确定的佣金与税费；以后做正式回测时，成本单独作为显式假设计算。

- **规则组 `rule`**：按现有 `strong_mainup` 综合分排序，取与 AI 最终数量相同的前 N 只。
- **AI 组 `ai`**：按 DeepSeek 最终风控评分排序，取前 N 只。
- **混合组 `hybrid`**：在进入深度分析的股票中，先把规则分和 AI 深度分分别转成当日百分位，再按 `50% 规则 + 50% AI` 排序取前 N 只。使用百分位避免两个分数量纲不同。
- **基准组 `benchmark`**：冻结候选池等权，不做规则或 AI 选择，用来判断筛选是否优于它实际面对的候选集合。

N 使用 Agent 面板的最终数量，默认 3。混合权重、模型名、温度、提示词版本、策略版本和候选池哈希都随批次持久化，历史批次不会因以后改配置而改变。

## 5. 买入与收益口径

### 5.1 日期定义

- `T`：四组结果生成的信号交易日。
- `entry_date`：`T` 之后第一个交易日。
- `entry_price`：`entry_date` 的开盘价。
- `ret1`：`entry_date` 收盘价 / `entry_price` - 1。
- `ret3`：信号日之后第 3 个交易日收盘价 / `entry_price` - 1。
- `ret5`：信号日之后第 5 个交易日收盘价 / `entry_price` - 1。
- `ret10`：信号日之后第 10 个交易日收盘价 / `entry_price` - 1。

`ret1` 表示买入当天从开盘到收盘的收益；`ret3/ret5/ret10` 使用同一买入价，分别表示持有到对应目标日收盘。

### 5.2 成交纪律

- 下一交易日尚未到达：`pending_entry`。
- 停牌、无开盘价或开盘价无效：`entry_unavailable`，不计算任何收益。
- 使用权威涨停价确认一字涨停且普通买方无法合理成交：`entry_unavailable`，原因记为 `limit_up_locked`。
- 目标日尚未到达：对应收益保持 `NULL`，状态为 `future_not_reached`。
- 目标日已到但行情缺失：记录 `target_bar_missing`，不得补零或改用邻近日期。

## 6. 数据结构

新增两张表，避免把实验元数据硬塞进现有 `picks` 或 `agent_judgments`：

### 6.1 `experiment_runs`

- `run_id`、`as_of`、`data_cutoff_at`、`status`
- `strategy_name`、`strategy_version`
- `model`、`temperature`、`prompt_version`
- `candidate_hash`、`candidate_count`、`final_count`
- `hybrid_rule_weight`、`hybrid_ai_weight`
- `created_at`、`finished_at`、`error_json`

### 6.2 `experiment_decisions`

- `run_id`、`group_name`、`ts_code`、`rank`
- `rule_score`、`ai_score`、`hybrid_score`
- `reason_json`、`risk_json`
- `entry_date`、`entry_price`、`entry_status`、`entry_reason`
- `ret1`、`ret3`、`ret5`、`ret10`
- 每个期限的目标日期、回填状态与失败原因

业务唯一键为 `(run_id, group_name, ts_code)`。同一成功批次再次执行时复用结果；强制重跑必须生成新 `run_id`，不得覆盖原实验。

## 7. API 与界面

### 7.1 API

- `POST /api/pipelines`：启动完整一键流程。
- `GET /api/pipelines/{run_id}`：返回步骤、进度、错误和四组摘要。
- `GET /api/experiments`：按信号日期、组别和状态分页查询。
- `GET /api/experiments/{run_id}`：查看一个批次的配置、候选池哈希和四组明细。
- `GET /api/experiments/summary`：返回各组已到期样本、平均收益、胜率和覆盖率；样本不足时只返回样本数与缺失原因。

### 7.2 选股流程页

- 页头增加「一键全流程」主按钮，保留刷新按钮。
- 固定步骤列表显示 `等待 / 运行中 / 成功 / 失败 / 不可用`。
- 失败时显示真实步骤和原因，不提供“忽略并继续”。
- 成功后显示四组结果标签页和数据截止时间。

### 7.3 台账页

- 默认按信号日期倒序分组。
- 支持日期、实验组、股票和成交状态筛选。
- 显示信号日、计划买入日、实际买入价、各期限收益及待回填原因。
- 同一股票在不同实验组中分别展示，确保组间对照可追溯。

## 8. 错误处理与恢复

- 预检、数据更新、完整性、AI、四组落库任一步失败，整个批次状态为 `failed`。
- 已经写入的真实行情和舆情保留；重跑依靠幂等键复用，不做跨网络步骤的假事务回滚。
- 四组必须全部成功落库后，批次才能标记 `succeeded`。
- 密钥、Authorization 请求头和完整模型响应不得进入日志或错误 JSON。
- 模型原始结构化结果可以落库，但必须先清除潜在凭据，并记录模型和提示词版本。
- AI 复盘、Agent 和设置页必须使用同一份 `settings.yaml + settings.local.yaml` 合并配置，不能出现设置页显示已启用而某个服务仍读取旧配置的情况。

## 9. 验证

### 9.1 自动测试

- OpenAI 兼容客户端 URL、鉴权头、请求负载、响应解析与错误路径使用 MockTransport 测试，不消耗真实额度。
- 一键流程覆盖成功、各步骤失败、恢复轮询、重复提交、强制重跑和四组原子完成条件。
- 收益追踪覆盖正常开盘、停牌、无开盘、一字涨停、未来未到、目标行情缺失和重复回填。
- 所有测试使用临时数据库，不读写 `data/market.duckdb`。

### 9.2 真实验收

- 使用真实密钥只发送一次最小无敏感内容请求，确认 `deepseekv4flash` 的 `/v1/chat/completions` 可用；不打印密钥和完整响应。
- 在真实库运行一次完整流程，核对四组共享同一批次、候选池哈希和数据截止时间。
- 使用一个已有历史日期的隔离数据库副本验证次日开盘买入和收益回填，禁止为了测试改真实台账。
- 浏览器验收按钮、步骤进度、刷新恢复、四组结果和按日期台账，确保无控制台错误和元素重叠。

## 10. 完成标准

- 用户只点击一次即可得到四组真实结果，期间无需继续操作页面。
- 当前批次完成后，所有四组数据可按信号日期查询并具备复现实验所需元数据。
- 后续每次一键运行都会先补齐已经到期的历史买入价与收益。
- 缺数据、无法成交、未来未到和真实的 0 收益在接口与页面中可区分。
- 系统只报告证据，不因结果为负而改口径；当前因子模型的负面结果继续如实保留。
